# 本机开发环境说明（Windows）

> **这份文档记录的是某一台具体电脑的环境搭建方式与已知限制**，不是项目本身的通用说明。
> 通用的「从 GitHub 取代码 → 在新电脑跑起来」流程请看 [另一台电脑接手指南.md](另一台电脑接手指南.md)。
>
> ⚠️ 本文含本机绝对路径（如 `C:\Users\11034\...`）。**换电脑时这些路径必须按实际情况替换**，第 九 节列了需要改的清单。

## 一、为什么单独有这份文档

这台电脑有几个环境特例，会导致「照着接手指南做却跑不起来」。把它们单独记下来，是为了避免以后每次重新踩一遍：

1. 系统 Node 是 v25（非 LTS），而项目 CI 要求 Node 22 LTS。
2. 文件沙箱禁止带管道的子进程，`npm ci` / `vite build` / `vite dev` 直接跑会失败。
3. 用户目录下的无签名 `.ps1` 脚本被系统拒绝执行。

这三条都不是项目的问题，是**本机环境**的问题。

## 二、Node 版本：系统 Node 25 与便携 Node 22

| | 版本 | 位置 | 用途 |
|---|---|---|---|
| 系统 Node | v25.7.0 | `C:\Program Files\nodejs` | 保持原样，**未改动** |
| 便携 Node 22 | v22.23.3 LTS (Jod) + npm 10.9.9 | `C:\Users\11034\node22` | **本项目使用** |

### 为什么不直接用系统 Node 25

项目 `.github/workflows/deploy-pages.yml` 与接手指南都要求 **Node 22 LTS**。v25 是奇数版（Current 通道，非 LTS），本地/线上行为可能有差异。

### 为什么不用 nvm-windows

本机当前账户**没有管理员权限**，而 nvm-windows 官方要求先卸载已有 Node.js（它需要接管 `C:\Program Files\nodejs` 符号链接，且每次 `nvm use` 都要管理员权限）。

因此改用**免管理员的便携版**：解压官方 zip 到用户目录即可，不碰系统 PATH、不影响其他项目。想回退直接删掉 `C:\Users\11034\node22` 目录。

### 便携版是怎么装的

```powershell
# 从 https://nodejs.org/dist/ 取最新 v22 LTS
# 下载 node-v22.x.x-win-x64.zip 后解压到 C:\Users\11034\node22
# 解压后目录里应直接看到 node.exe（即把 zip 内层的 node-v22.x.x-win-x64\ 内容提上来）
```

## 三、两个本机脚本

这两个文件都在**仓库根目录**，且都已加入 `.gitignore`（含本机绝对路径，不应入库）。

### `npm22.cmd` —— 推荐用法

用 Node 22 执行一条 npm 命令。**`.cmd` 不受 PowerShell 脚本策略限制**，因此最可靠。

```powershell
.\npm22.cmd run dev        # 启动开发服务器
.\npm22.cmd run build      # 生产构建
.\npm22.cmd run test:unit  # 单元测试
.\npm22.cmd run typecheck  # 类型检查
```

它做的事：把 `C:\Users\11034\node22` 插到 PATH 最前，设置 `npm_config_cache`，然后调用该目录下的 `npm.cmd`。

### `use-node22.ps1` —— 切换整个会话

如果你希望**当前会话**里 `npm` / `node` 都走 Node 22：

```powershell
. .\use-node22.ps1
```

注意开头的点号（dot-source），否则 PATH 改动不会留在当前会话。

**如果被脚本策略拒绝**，用这种方式调用：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\use-node22.ps1
```

> 维护提醒：这个文件**必须保持纯 ASCII**。Windows PowerShell 5.1 会把无 BOM 的 UTF-8 文件按 ANSI 解码，中文注释会打乱字节并破坏语法（这个坑已经踩过一次）。

## 四、npm 缓存必须在工作区内

本机默认 npm 缓存是 `C:\Users\11034\AppData\Local\npm-cache`，位于**工作区之外**，会被文件沙箱拒绝写入，报 `EPERM`。

因此本机统一把缓存放在工作区内的 `.npm-cache/`（已加入 `.gitignore`）。

- `npm22.cmd` 会自动设置好，无需手工处理。
- 如果直接跑 `npm`，需要先设置：

```powershell
$env:npm_config_cache = Join-Path (Get-Location).Path '.npm-cache'
```

## 五、已知限制 A：文件沙箱禁止带管道的子进程

> **当前状态：已解除。** DSH 文件策略现已改为 `danger-full-access`，本节描述的失败不再出现。
> 保留此节是因为：该限制由 DSH 的沙箱策略决定，**策略回退时会再次生效**；而且它解释了
> `.npm-cache`（第四节）和 `npm22.cmd` 存在的原因，不要误删。

**现象**：`npm ci`、`npm run build`、`npm run dev` 在默认沙箱下失败，报 `spawn EPERM` 或 `EPERM: operation not permitted`。

**原因**：本机 DSH 处于 `workspace-write` 模式，该模式（以及只读模式）**禁止程序打开命名管道**。而 Node.js 的 `child_process` 默认用管道捕获子进程输出，Vite/esbuild 的整个通信机制都依赖管道。

**影响范围**：任何需要 esbuild 子进程的命令，即构建、开发服务器、以及 `npm ci` 里的 postinstall 脚本。

**应对**：这些命令需要在更宽权限下运行（`danger-full-access`）。表现为每次执行会弹一次授权确认。

**不受影响**：`typecheck`（纯 TypeScript 编译）、`git`、文件读写等。

## 六、已知限制 B：用户目录下的无签名 .ps1 被拒绝执行

**现象**：任何位于用户目录的无签名 `.ps1` 都报「未对文件进行数字签名。无法在当前系统上运行该脚本。」——**即使执行策略已是 `RemoteSigned`**（按设计应允许本地无签名脚本）。

**已经查明的事实**：

| 检查项 | 结果 |
|---|---|
| 执行策略（`CurrentUser`） | `RemoteSigned`（搭建时已设置） |
| `MachinePolicy` / `UserPolicy` | `Undefined`（无组策略下发） |
| 机器是否受组织管控 | **否**（AzureAdJoined / DomainJoined / WorkplaceJoined 全为 NO） |
| `CiPolicies\UserPolicies` | **不存在** → 策略非企业下发 |
| Smart App Control | **关闭** |
| WDAC 策略文件 | `CiPolicies\Active\` 下有 8 个 `.cip`，属 **Windows 11 内置** |
| MOTW / Zone.Identifier 标记 | 无 |
| `PSExecutionPolicyPreference` 环境变量 | 未设置 |

**已确认的对照结论**：

- `C:\Program Files\nodejs\npm.ps1` 同样是 `NotSigned`，但**能正常运行** → 存在基于**路径**的信任规则（系统目录受信）。
- 同一个脚本加 `-ExecutionPolicy Bypass` 就**能运行** → 说明是执行策略层面，而非 WDAC 强制执行。

**结论**：确切机制未完全定性（`RemoteSigned` 拒绝本地无签名文件本身不符合标准行为），但**实际应对明确**，且这台机器没有任何组织管控或安全异常。

**应对**：

1. 优先用 `.cmd`（完全不受脚本策略约束）。
2. 必须用 `.ps1` 时，显式加 `-ExecutionPolicy Bypass`。

**对本项目的影响：为零。** 已验证项目里唯一使用 PowerShell 的 npm 脚本 `clean:workspace`（它用的是 `-ExecutionPolicy Bypass -Command "内联脚本"`，不是脚本文件）**正常运行，退出码 0**。

### 本机特例：CLI 必须关闭遥测

**现象**：不带 `DO_NOT_TRACK=1` 时，任何 supabase 命令都失败：

```
EPERM: operation not permitted, open 'C:\Users\11034\.supabase\telemetry.json.tmp.<uuid>'
Bun v1.3.13 (Windows x64 baseline)
```

**关键排查结论**：这**不是** DSH 文件沙箱造成的 —— 在 `danger-full-access` 下依然复现。而且用 PowerShell `Set-Content` 写同一个目录**完全正常**。所以是这台机器对 **supabase.exe（Bun 编译的二进制）** 的写入限制，和第五节/第六节的 WDAC 加固属于同一类。

**解法**：设 `DO_NOT_TRACK=1`（或 `SUPABASE_TELEMETRY_DISABLED=1`），两者单独都有效。该变量已写进 `npm22.cmd`，所以通过它跑的命令都不受影响。

## 十、换电脑时需要改什么

换到新电脑时，这份文档里**不能直接照搬**的部分：

1. **`C:\Users\11034\node22`** —— 用户名和盘符按实际情况改。出现在 `npm22.cmd` 和 `use-node22.ps1` 里。
2. **`C:\Users\11034\AppData\...`** —— 同上。
3. **Node 版本策略** —— 如果新电脑能装 nvm，直接用 nvm 装 Node 22 更省事，就不需要便携版和这两个脚本了。
4. **文件沙箱限制（第五节）** —— 这是 DSH 工具的限制，不是 Windows 的，换电脑后是否出现取决于新环境的沙箱配置。
5. **脚本签名限制（第六节）** —— 取决于新电脑的 WDAC / 执行策略状态，不一定会复现。

**通用部分**（Node 22 LTS 要求、npm 缓存位置、`.env.local` 配置）在接手指南里已有说明，换电脑时以那份为准。
