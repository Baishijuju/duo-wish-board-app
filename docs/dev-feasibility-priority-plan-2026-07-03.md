# 双人人生愿望清单 研发主导评估（前后端一体）

> 角色前提：本文件以资深 Vue + TypeScript 开发视角输出，目标是把三份方案转成可执行研发决策，并明确哪些需求当前不清晰、会导致扯皮或返工。

## 0. 结论先说
- 这轮需求里，70% 是高收益快改，适合立刻做。
- 20% 是方向对但定义不够，直接做会返工。
- 10% 涉及策略与数据闭环，没有埋点/实验就别拍脑袋上线。

研发立场：不当被动执行层，要参与需求裁剪、交互定义和验收标准共建。

---

## 1. 哪些是好做、明确、改动快的
## 1.1 可在 1-3 天完成（低风险）
- 空间页默认态减重：默认仅展示领奖主流程，其它折叠到管理层。
- 清单条目去重复：统一为主值 + 副值 + 右侧状态位。
- 详情页推进 CTA 固定：保证首屏稳定可见。
- 长文案折叠策略：超阈值自动截断 + 展开。
- 页面级控件密度约束：首屏控件数量上限、同屏层级上限。

原因：
- 基本都是模板层和样式层改造。
- 业务数据结构无需重构，主要是展示逻辑收敛。
- 可以在现有 Vue SFC + composables 结构内平滑落地。

## 1.2 可在 3-7 天完成（中风险）
- 行动层/管理层模式切换（全局一致）。
- 状态语义统一（文案、颜色、图标）。
- 回顾页“核心三指标 + 其余折叠”的信息重排。

原因：
- 会影响多个页面，需要统一组件抽象。
- 需要避免每页各写一套状态映射，最好抽到共享层。

---

## 2. 哪些是讲不清、容易甩锅的需求
## 2.1 “看起来更舒服”“更有高级感”
问题：只有感受，没有验收标准。
风险：设计稿来回改，研发背返工锅。

研发要求补齐：
- 必须给量化约束，如首屏控件数、文案字数、点击步数。
- 必须给页面主任务定义，不允许一页多个同级主任务。

## 2.2 “先做一个增长机制看看”
问题：没有事件定义和目标指标。
风险：功能上线后无法证明有效，最后说研发实现不好。

研发要求补齐：
- 先定义埋点事件、口径和观察窗口。
- 先跑最小实验，再决定是否扩大。

## 2.3 “不改能力，只是调一下结构”
问题：很多时候结构调整实质改变行为路径。
风险：产品说没改需求，用户行为却变了，结果甩给开发。

研发要求补齐：
- 所有结构改动必须附行为路径前后对比图。
- 验收要包含关键路径点击步数和转化变化。

---

## 3. 我认为当前方案里不好的点（直接说）
## 3.1 目标太多，阶段边界不清
- 同时要留存、要美观、要增长、要品牌强化。
- 这会导致版本 scope 失控，最后每项都做半套。

建议：
- 当前版本只追两个结果：降低默认态负担 + 提升高频动作完成率。

## 3.2 缺统一组件契约
- 三份文档都提到“统一状态、统一骨架”，但没给组件接口规范。
- 没有契约就会演变成每页一套实现。

建议：
- 先定义基础组件协议，再改页面。

## 3.3 对数据闭环依赖高，但埋点尚未落地
- 多个建议依赖 D1/D7、点击步数、退出率。
- 如果不上埋点，后续只能凭感觉复盘。

建议：
- 埋点属于 P0，不是 P1。

## 4. 技术优先级（研发版本）
## P0（本周，先拿确定收益）
1. 建立页面主任务和控件密度约束（配置化）。
2. 清单条目骨架统一（主值/副值/状态位）。
3. 空间页默认态精简到领奖主流程。
4. 详情页推进 CTA 固位。
5. 埋点基础层上线（曝光、点击、退出、中断）。

交付标准：
- 无新增核心逻辑回归。
- 首屏可见控件数符合阈值。
- 关键路径点击步数下降可测。

## P1（下周，做结构升级）
1. 行动层/管理层双态框架。
2. 状态语义中心化（文案/颜色/图标统一映射）。
3. 回顾页信息层级重排。

交付标准：
- 跨页状态呈现一致。
- 设计改稿不需要改业务逻辑，只改配置与样式。

## P2（再下一阶段，做增长）
1. 连续推进激励（streak）。
2. 协同提醒机制（低打扰）。
3. 默认排序个性化。

交付标准：
- 有实验对照，不做无指标上线。

## 5. 我给产品经理和 UI 设计师的技术建议（可直接用）
## 5.1 用可配置规则替代反复改稿
建议新增一层 UI 规则配置：
- textLimit.main = 18
- textLimit.sub = 28
- screen.maxControls = 8
- list.itemLayout = compact | expanded

收益：
- 产品和设计改规则即可，不用每次改模板代码。

## 5.2 建立页面骨架组件，而不是页面复制
建议新增通用组件：
- ActionCard：高频动作容器。
- ManagePanel：低频管理容器。
- StatusChip：统一状态语义。
- MetricRow：主副值标准行。

收益：
- 减少视觉漂移和实现分叉。
- 新页面可复用，维护成本下降。

## 5.3 引入 useDensityMode 与 usePriorityLayout composable
能力：
- 根据页面和设备动态切换 compact/comfortable。
- 主任务区块自动前置，低频区块自动后置/折叠。

收益：
- 不是人工“每页调像素”，而是策略驱动布局。

## 5.4 状态映射中心化
建立统一状态字典：
- status -> label -> tone -> icon -> actionHint

收益：
- 避免多页面文案和颜色口径冲突。

## 5.5 埋点 SDK 封装成 typed event
TypeScript 事件定义示例方向：
- event: page_view | action_click | panel_toggle | abandon
- payload: page, module, action, source, duration

收益：
- 编译期约束事件字段，避免脏数据。

## 6. 研发不该当底层执行的具体机制
## 6.1 需求进入开发前的四件套（没有就不排期）
1. 主任务定义（该页用户最先做什么）。
2. 可量化验收（步数、控件数、转化目标）。
3. 交互状态图（默认、展开、异常、空态）。
4. 数据口径（埋点事件和计算方式）。

## 6.2 评审制度建议
- 产品评审：确认业务目标与优先级。
- 设计评审：确认主次层级和组件复用策略。
- 技术评审：确认改动边界、依赖、回归范围。
- 联合验收：按指标，不按主观争论。

## 6.3 返工防线
- 未定义清楚的“体验词”不进开发。
- 非功能性目标必须转成量化阈值。
- 需求变更超过 30% 自动触发重新评审。

---

## 7. 当前最建议立刻做的 8 条任务
1. 空间页默认态只留领奖主流程。
2. 清单页条目统一骨架并去重信息。
3. 详情页推进 CTA 固位并强化可见性。
4. 长文案统一折叠策略。
5. 首屏控件数和层级约束落地。
6. 状态语义统一映射字典。
7. 最小埋点事件集接入。
8. 建立 ActionCard 与 ManagePanel 两个基础组件。

---

## 8. 最终态度
我支持产品和设计目标，但开发不会再做“语义不清的美化冲刺”。

要快、要好、要可持续，唯一办法是：
- 先把高频路径做短
- 再把默认信息做薄
- 最后用组件化和埋点把迭代变成可验证工程

这不是抬杠，这是对结果负责。
